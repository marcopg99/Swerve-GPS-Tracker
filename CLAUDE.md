This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Single-module Android app (`:app`) that records GPS tracks to a local Room database, displays them on an OpenStreetMap-based map, and exports them as GPX files. Tracks can have a **cover image** and store a computed **distance**. Package: `com.mpg99.gpstracker`. UI strings are in Spanish.

- Kotlin 2.0.21, AGP 8.7.3, Compose BOM 2024.12.01
- `minSdk = 29`, `targetSdk = 35`, JDK 17
- Version catalog in `gradle/libs.versions.toml` — add new dependencies there, not directly in `app/build.gradle.kts`
- Image loading via **Coil** (`io.coil-kt:coil-compose`) — loads cover images from internal-storage `File` paths, offline.
- Release builds are signed with the **debug keystore** (`signingConfig = signingConfigs.getByName("debug")` in `app/build.gradle.kts`), so `assembleRelease` produces an installable, signed APK. Installing over a copy signed with a different key fails with a package-conflict error — uninstall first.

## Commands

```bash
./gradlew assembleDebug                 # build debug APK
./gradlew installDebug                  # build + install on connected device/emulator
./gradlew test                          # JVM unit tests
./gradlew connectedAndroidTest          # instrumented tests (needs device)
./gradlew :app:testDebugUnitTest --tests "com.mpg99.gpstracker.SomeTest"   # single test
./gradlew lint                          # Android lint
./gradlew clean
```

There is no separate lint/format step beyond Android lint; Kotlin style is `kotlin.code.style=official`. Room schemas are generated by KSP, not kapt — if Room codegen seems stale, `./gradlew clean` and rebuild.

## Architecture

Layering (all under `app/src/main/java/com/mpg99/gpstracker/`):

- **`data/`** — Room. `Track` (1) ↔ `TrackPoint` (N) with `ForeignKey.CASCADE`. `Track` carries `coverUri: String?` (absolute path to a cover image in internal storage) and `distanceMeters: Double` (maintained, not derived at read time). `TrackDao.observeTrackSummaries()` returns `TrackSummary` (a non-entity projection that also exposes `coverUri` and `distanceMeters` plus the joined `pointCount`). `AppDatabase` is a manual lazy singleton via `AppDatabase.get(context)`; DB name `gpstracker.db`, **currently version 3**. Schema changes need a `Migration` added to the `addMigrations(...)` call: `1→2` added `coverUri`, `2→3` added `distanceMeters`. `TrackRepository` wraps the DAO and is the single API surface the rest of the app uses. For thumbnails without a cover it also exposes `routePreview(trackId, pointCount)`: a thinned list of `LatLon` (≤80 points, from the lightweight `TrackDao.getPointCoords` query) cached in memory under the key `"trackId:pointCount"`, so a track that gained points is recomputed.
- **Distance tracking** — `Track.distanceMeters` is maintained three ways, all using `util.haversineMeters` over consecutive points so the value always matches what the detail screen computes live: (1) `TrackingService` keeps a running total as points arrive and calls `repo.setDistance`; (2) `TrackRepository.finishTrack` recomputes accurately from all stored points on stop; (3) `TrackRepository.importTrack` computes it for imported GPX. `GPSTrackerApp.onCreate` runs `repo.backfillDistances()` once in a background coroutine to fill in tracks recorded before this column existed (rows where `distanceMeters == 0`). The **detail screen computes its own distance from points** (`TrackDetailViewModel`) rather than reading the column, so it is always correct even mid-recording.
- **`service/TrackingService`** — foreground service (`foregroundServiceType="location"`) that owns the FusedLocationProvider subscription and writes points through the repository. Started/stopped via the static `TrackingService.start(context)` / `stop(context)` helpers. Exposes its current state to the UI through a **process-wide static `StateFlow<TrackingState>`** (`TrackingService.state`) — that is intentionally the source of truth for "is a track currently being recorded?", because the service may outlive the Activity. Also keeps `lastLat/lastLon/runningDistance` fields (reset on start/stop) to maintain live distance. Constants for sampling cadence (`LOCATION_INTERVAL_MS = 5s`, `LOCATION_FASTEST_INTERVAL_MS = 2s`, `LOCATION_MIN_DISTANCE_M = 5m`) live in its companion.
- **`ui/`** — single-Activity Compose app. `MainActivity` → `AppNavigation` (NavHost with `home`, `record`, `list`, `detail/{trackId}` routes). Each screen has its own `ViewModel` with a hand-rolled `viewModelFactory` companion that pulls the repository off `GPSTrackerApp` via `APPLICATION_KEY`. There is **no DI framework** — `GPSTrackerApp.repository` is the injection point; new ViewModels should follow the same `Factory` pattern (see `HomeViewModel`).
  - **Navigation** — `home`, `record` and `list` are top-level tabs sharing `ui/components/AppBottomBar` (Inicio · central record button · Rutas; the record button turns coral while `TrackingService.state.isTracking`). Each of those screens takes `onNavigate: (NavTab) -> Unit` and puts the bar in its own `Scaffold(bottomBar = …)`; `AppNavigation` pops back to `home` rather than stacking tabs. They have no top app bar or back button. `detail` is a sub-screen without the bar.
  - **`ui/home`** — dashboard: header (rounded logo + "Swerve"), two totals tiles (total distance = sum of `distanceMeters`, track count), the "Última ruta" card (cover/route shape + name + date + distance/duration chips, tappable to detail) and up to two "Recientes" rows. `HomeViewModel.uiState` is a single `HomeUiState` flow. It does **not** contain the recording controls or the GPX import button.
  - **`ui/record`** — `RecordScreen`/`RecordViewModel`: the actual recording UI (runtime-permission requests, `HH:MM:SS` clock, live distance and point count, the route shape so far while recording, big round Iniciar / wide coral Detener). `RecordViewModel.liveStats` derives count, distance and a thinned route from `repo.observePoints`. This is where a new track is created via `TrackingService.start/stop`. Stopping does not navigate anywhere.
  - **`ui/list`** — track list as compact rows (thumbnail, name, date, distance/duration chips on one line) with a hamburger menu (`TrackMenu`: Compartir GPX, Borrar) to the right of the title, so the chips keep the full width; add new per-route actions there. The title is **always two lines tall** (`minLines = maxLines = 2`, ellipsis) so all rows have the same height; the thumbnail has a fixed 88×108 dp size. Don't size it with `IntrinsicSize.Min`/`fillMaxHeight`: that under-counted the two-line title and squeezed the chips until their text was clipped (empty pills). The GPX **import** button lives only here (top right, up-arrow icon).
  - **`ui/detail`** — full-height osmdroid map with floating back / cover-picker buttons, and a rounded bottom sheet (name + rename, distance and duration tiles, points count in small text under the date, "Exportar GPX"). The cover is set/replaced through the Android **photo picker** (`ActivityResultContracts.PickVisualMedia`). **Points count is shown only here**; home and list show distance instead. There is no `Scaffold` here, so the root is a `Surface` that sets the content color — without it text and icons default to black; translucent floating buttons also need an explicit `contentColor`.
  - **`ui/trim`** — `TrimScreen`/`TrimViewModel` (route `trim/{trackId}`, opened from the scissors button in detail, shown only for finished tracks with ≥3 points). Map + `RangeSlider` + two numeric point inputs (1-based, with −/+). Kept range is green, dropped ends dotted grey. Saving calls `TrackRepository.trimTrack(trackId, fromIndex, toIndex)`, which **permanently deletes** the points outside the range and updates `startTime`/`endTime`/`distanceMeters` in one DAO transaction (no schema change). `TrackDetailViewModel` re-reads the track on every points emission so the detail screen refreshes after a trim. `markerIcon`, `rememberMapView` and `FloatingCircleButton` are `internal` in `TrackDetailScreen.kt` and shared with it.
  - **`ui/components/`** — shared pieces:
    - `TrackCover.kt`: draws the cover image (Coil `AsyncImage` of a `File`) if set, otherwise the **bare shape of the route** (no map behind it) via `RouteShape`, otherwise a placeholder icon. The `TrackSummary` overload loads the preview from `repo.routePreview`, and skips it when a cover exists.
    - `RouteShape.kt`: Canvas that scales/centers a `List<LatLon>` (longitude compressed by cos(lat)) with a halo, hollow start dot and filled end dot.
    - `Chips.kt`: `StatChip` (pill) and `StatTile` (bordered label + big value + unit; `compact` for tight rows).
    - `AppBottomBar.kt`: `NavTab` + the bottom bar described above.
- **`gpx/GpxExporter`** — writes a GPX 1.1 file to `filesDir/gpx/` and returns a share `Intent` via `FileProvider`. The authority is `${applicationId}.fileprovider` and is wired in `AndroidManifest.xml` + `res/xml/file_paths.xml`; don't change one without the other.
- **`util/Format.kt`** — shared formatting helpers (`formatDateTime`, `formatDateShort`, `formatGpxTime`, `distanceParts` / `formatDistance`, `formatDuration`, `formatClock`, `haversineMeters`). Reuse these rather than reformatting in screens.
- **`util/RoutePreview.kt`** — `downsample(points, maxPoints)`: evenly thins a list keeping first and last; used for route shapes.
- **`util/CoverStore.kt`** — copies a picked image `Uri` into `filesDir/covers/` (timestamped filename to defeat image caches; deletes the previous file) and returns the absolute path stored in `Track.coverUri`. Cover files are deleted when their track is deleted (see `TrackListViewModel.deleteTrack`).

**Theme** — `ui/theme/Theme.kt` forces a **dark** Material 3 palette always: dynamic color is disabled and there is no light scheme. Near-black green ground (`#0D120F`), two surface steps (`surfaceContainer` `#151C17`, `surfaceVariant` `#1D2620`), a single emerald accent (`AccentGreen` `#2FBF71`) and coral (`StopButtonColor`) reserved for recording/stop; `DangerColor` for destructive actions and `RouteBackdropColor` behind route shapes. Use the exported constants instead of new hex values. Typography is the system default (no custom fonts). `MainActivity` forces light system-bar icons via `enableEdgeToEdge(SystemBarStyle.dark(...))`, and `res/values/themes.xml` + `values-night/themes.xml` both use the dark `@color/app_background` (keep it equal to the theme's background).

**Logo / icon** — `res/drawable/logo.xml` (header logo, includes its own `#0D120F` background) and `ic_launcher_foreground.xml` (adaptive icon, scaled/offset to sit inside the safe zone; no opaque fills beyond the route and arrival dot so it doubles as the monochrome icon) draw the same mark: the angular S route with an emerald→coral gradient, a hollow departure dot and a coral arrival dot with two GPS-signal rings. `ic_launcher_background` is the solid `#0D120F`. With `minSdk = 29` the adaptive icon is always used; the legacy `mipmap-*` PNGs are leftovers.

Map rendering uses **osmdroid** (`org.osmdroid:osmdroid-android`), not Google Maps. `GPSTrackerApp.onCreate` configures osmdroid's user agent and points its tile cache at `getExternalFilesDir("tiles")` — this must run before any `MapView` is inflated, so keep that init in the `Application` subclass.

### Permissions & runtime behavior

The manifest declares `ACCESS_FINE_LOCATION`, `ACCESS_COARSE_LOCATION`, `ACCESS_BACKGROUND_LOCATION`, `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_LOCATION`, and `POST_NOTIFICATIONS`. The service self-stops if `ACCESS_FINE_LOCATION` is missing — runtime permission requests are the UI layer's responsibility before calling `TrackingService.start`. On Android 14+ (`UPSIDE_DOWN_CAKE`) the service calls `startForeground` with the explicit `FOREGROUND_SERVICE_TYPE_LOCATION` flag; preserve that branch when touching `startForegroundCompat`.
